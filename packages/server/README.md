# Journey server

This Worker serves `/v1/*` with Hono and non-API paths from the web build (`ASSETS`, with SPA fallback). Each journey lives in one SQLite-backed Durable Object (`EnclaveFresh`). A second, fixed-name SQLite-backed object (`RegistryFresh`, ID `registry-v2`) holds accounts and the operator registry. We chose it instead of D1 to avoid a second storage product. The `v2-fresh-storage` migration switches bindings to fresh SQLite classes; `v3-delete-old-storage` deletes the unbound old `Registry` and `EnclaveObject` classes, clearing every account, journey and journey object. API errors are always `{ "error": { "code": "..." } }` and never include internals.

## API

| Method and path | Purpose |
|---|---|
| `POST /v1/auth/email/start` | `{email,returnPath?}`: send a magic link; always 202 for valid input, with per-IP and per-email limits. Optional return path accepts only `/agent-sessions/:id` and is encoded after the link's `#`; invite secrets are rejected. |
| `POST /v1/auth/email/verify` | `{token}`: consume a 15-minute link; return a registration or sign-in challenge and a 12-hour cookie. |
| `POST /v1/auth/passkey/register/options`, `/register/verify` | Request a resident passkey with user verification and a PRF result. Verify accepts `{response,sealed:{version:1,identity,signing}}` and saves that credential and its encrypted copy of the person keys together. Adding another requires a recent passkey confirmation or a recovery session. No PRF support or invalid sealed keys means nothing is saved. |
| `POST /v1/auth/passkey/login/options`, `/login/verify` | With an email-link session, use any registered passkey. A successful assertion selects that credential's encrypted person-key copy. A verified session can request options again to unlock a new tab. |
| `POST /v1/auth/passkey/start`, `/finish` | Sign in without an email link: discoverable passkey options (no credential allow-list), a five-minute pre-session challenge cookie, and a verified 12-hour session after assertion. |
| `POST /v1/auth/logout` | Revoke the cookie. |
| `GET /v1/me/keys` | Return only the encrypted person-key copy for the passkey used in this session, or the redeemed backup code's sealed copy during recovery. No plaintext private keys. No-store response. There is no PUT route; copies are saved when credentials or backup codes are registered. |
| `GET /v1/me/passkeys`, `DELETE /v1/me/passkeys/:id` | List each credential's name, creation and last-use time and remaining backup-code count; remove a credential after fresh confirmation, but never the last credential. Replace by adding then removing. |
| `PUT /v1/me/backup-codes` | After recent passkey verification, replace all backup codes with exactly eight client-generated verifier hashes and eight separately sealed copies of the same person keys. Invalid or extra fields are rejected. |
| `POST /v1/auth/backup-code/redeem` | Hash a client-derived verifier to find and consume one code atomically, then issue a ten-minute session usable only to read its sealed copy and register a new passkey. Per-IP and per-verifier lookup limits apply. No email is needed. |
| `POST /v1/journeys` | Create with `{id,creator:{id,recipient,signingKey},control:{proof,envelope},wraps,recoveryWrap}`. The signed creation proof pins the creator and supplies the minimum client version. Legacy history and genesis blobs are refused. The creator email comes from the verified sign-in session. Each wrap is `{principal,epoch,wrap}`. |
| `GET /v1/journeys` | List accessible journeys and the account's principal IDs. |
| `POST /v1/journeys/:id/seq` | Reserve `{seq,epoch}` for five minutes, then use core `seal` to include that sequence in authenticated metadata. |
| `POST /v1/journeys/:id/records` | `{envelope}`: store at the reserved sequence, maximum plaintext size 1 MiB. |
| `GET /v1/journeys/:id/records?after=&limit=` | Read ciphertext after a sequence, up to 100 records per request. |
| `POST /v1/journeys/:id/log` | Append `{control:{proof,envelope},wraps?}` atomically. Verify signatures, actor, journey, ciphertext binding, chain and current Bend authority before deriving access effects. Person admission (including temporary support) requires exactly one wrap for each epoch from 1 through the current epoch; agents receive only the current-epoch wrap. Rotation requires exactly the remaining recipients at the next epoch. Plain `accessChanges` and legacy writes are refused. |
| `GET /v1/journeys/:id/log?after=` | Fetch up to 1,000 signed public controls with encrypted labels; default `after=-1`. |
| `GET /v1/journeys/:id/protocol` | Return the signed minimum version and required formats to an authenticated current member, even when their client is too old. Stage 1 also requires `artifact-v1`; Stage 2 additionally requires `project-v1`. No content is returned. |
| `GET /v1/journeys/:id/wraps/me` | Fetch only the caller's epoch wraps. |
| `POST /v1/journeys/:id/blobs` | `{size}`: stage a server-generated blob ID for one hour under the current epoch and uploader. Size is raw bytes, from zero through 25,000,000 inclusive. Returns `{id,journey,epoch,size,expiresAt}`. |
| `PUT /v1/journeys/:id/blobs/:blob` | Send binary ciphertext with `X-Blob-Descriptor` containing the core descriptor. Authenticate as the uploader; count actual streamed bytes, verify the digest, then recheck current access, epoch, version and stage expiry before marking complete. |
| `GET /v1/journeys/:id/blobs/:blob` | Download committed, live binary ciphertext after checking current member access. Returns `application/octet-stream`, an opaque `.encrypted` attachment name, `X-Blob-Descriptor`, `nosniff` and `no-store`. No public or bearer download URL. |
| `GET /v1/journeys/:id/export` | Stage 1 returns the core `artifact-v1` archive with signed `controls`, encrypted `envelopes`, only the caller's `wraps`, surviving blob descriptors/ciphertext, and `unavailableDeletedBlobs`. Blob ciphertext is base64 only in this JSON archive. Stage 0 retains its existing `log/envelopes/wraps` response. The client verifies the archive and age-encrypts it with core. |
| `POST /v1/journeys/:id/invites` | `{inviteIdHash,expiresAt,support?,email?,inviteId?}`: create a one-use invite that expires within seven days. With `email`, the request also carries the matching client-generated secret `inviteId` so the Worker can email the link; the address is not stored. `support:true` marks a Wayfinding support invitation; admission must be read-only and expires when the invite expires. |
| `GET /v1/journeys/:id/invites/pending` | List pending public keys, support marker and expiry for a holder's device. |
| `POST /v1/invites/accept` | `{inviteId,principal:{id,recipient,signingKey}}`: consume an invite and wait for the holder's add and wrap. |
| `POST /v1/agent-sessions`, `GET /v1/agent-sessions/:id` | Request `{journeyId,agentPublicKey:{recipient,signingKey},requestedScope,remembered?}`; receive a six-digit code and approval URL, then poll the opaque session ID. GET returns the public recipient and signing key, requested scope, and remembered flag for the approval screen; it never returns the code. |
| `POST /v1/agent-sessions/:id/approve` | A person with recent passkey verification sends `{code,principal,scope,expiresAt,wrap,control}`; the signed add must match the server-owned pending agent registration. |
| `GET /v1/admin/registry` | Constant-time checked `Bearer ADMIN_TOKEN`; returns registry metadata only. |

## Sign-in and invites

Every state-changing request needs `Origin: https://app.wayfinding.support` and `X-Wayfinding: 1`. A person sends the httpOnly, Secure, SameSite=Strict `wayfinding_session` cookie and `X-Principal` on journey routes. Magic-link start always follows the same account-independent issuance path and returns 202, whether the account exists or not. Email addresses are normalized and hashed with HMAC-SHA-256 under `EMAIL_HASH_KEY`. A verified email session can register or request a login assertion, but cannot access journeys until passkey verification succeeds. WebAuthn checks `RP_ID`, `ORIGIN`, required user verification, a single-use challenge, and the credential counter. Login options include `extensions.prf.eval.first`: a stable app-wide 32-byte input derived from `EMAIL_HASH_KEY`, not a new deployment secret. Each passkey has its own PRF output; the client seals the same person keys separately under each output and the server returns only the copy for the verified credential. Registration and sealing are saved in one SQLite transaction. A client reports whether PRF was enabled; the server cannot independently prove that a browser returned a usable PRF output, so the client must test it before submitting its encrypted keys. Backup codes are 16 random bytes each, displayed once in grouped Crockford base32; HKDF derives independent verifier and wrapping keys. The server stores only SHA-256 hashes of the verifier strings and AES-GCM-sealed key copies. A code cannot open journeys: its short-lived session may only read the sealed copy and enroll a new passkey; all other API routes are denied until enrollment succeeds.

The class deletion migration permanently wipes all old registry and journey Durable Objects; prior sessions and credentials stop working. Everyone must sign up again and save their new backup codes.

Journey routes require `X-Client-Version` of at least `0.1.4` and `X-Control-Format: control-proof-v1`. The durable signed minimum may require a later version. Stage 1 journeys require at least `0.1.5` and `X-Artifact-Format: artifact-v1` as well. Stage 2 journeys require at least `0.1.6` and `X-Project-Format: project-v1` in addition to those two capabilities. A minimum-raising control must satisfy the resulting minimum and capabilities. Unsupported readers receive 426 before any partial content; journey listings propagate this error rather than silently omitting incompatible journeys. Bend decides current read access, content writes, reservations, blob staging/references/cleanup, pending rotation and client compatibility; capability headers do not grant authority.

The Stage 0 schema upgrade is separate from the earlier class deletion. It purges existing test journeys without migration and keeps accounts, credentials, sessions and agent registrations. Enclave schema version 2 clears logs, records, wraps, access, reservations and metadata; Registry clears only journey-related tables. Creation establishes new trust from its signed proof, without legacy history.

The guide makes 32 random bytes, puts them after `#` in the invitation URL, and posts their base64url SHA-256 digest as `inviteIdHash`. For email invitations only, the link secret passes through the Worker so it can email the link via `MAGIC_EMAIL` from `noreply@wayfinding.support`, with `hello@wayfinding.support` as reply-to; neither the email address nor the secret is saved in invitation storage. The fragment never goes to the server when the recipient opens the link. Invitations sent by email are limited per journey and account. The invitee submits the random value as `inviteId`, proves email control and registers a passkey. The server consumes the invite once and holds the new principal as pending. A guide's device verifies the signed log and posts a `member.add` control and wraps for every epoch from 1 through the current epoch, then the new principal can read. The normal admission role comes from current signed settings. A support invitation produces a signed support marker and read-only, expiring membership; the Worker rejects any writable or extended support access change, and the signed-log verifier refuses management grants to support members. `inviteSecretProof` is reserved for a later proof design; this version checks the hash preimage supplied as `inviteId`.

For removal an authorized person posts a signed `member.remove` control. The object immediately denies that principal and a removed person's agents, revokes their links and blocks content writes and reservations until a remaining guide posts `key.rotate` with exactly the next epoch and wraps for remaining principals. Authorized personal and guide controls still work while rotation is pending. Old ciphertext remains under the earlier key. Devices retry an interrupted rotation.

## Agent signatures

Unapproved sessions expire after ten minutes; five wrong approval codes lock a session. Creation is limited to ten requests per IP per minute. Approval checks a matching six-digit code and a passkey verified within five minutes. An approved session expires within eight hours. A remembered agent can last up to 90 days. Agents cannot call passkey endpoints or send access-list changes or key wraps through the log route. Every signed journey request sends `X-Agent-Session`, `X-Agent-Timestamp` (Unix milliseconds), `X-Agent-Nonce` (fresh random string) and `X-Agent-Signature` (base64url Ed25519 signature). Sign UTF-8 of the following fields separated by a single LF, without a trailing LF:

```
METHOD
PATH_WITH_QUERY
BASE64URL_SHA256_EXACT_BODY_BYTES
TIMESTAMP
NONCE
```

GET has an empty body. The path has no host or fragment. The server rejects timestamps more than 60 seconds away, bad signatures, expired agents and reused nonces. Nonce pairs remain in the registry for 60 seconds. After approval, the agent signs a request for its wrap.

## Storage and trust

Plain storage: journey ID and name, creator email in the creator's registry row only (also held with the sign-in token for 15 minutes and the session for 12 hours, so journey creation needs no retyping), record metadata and size, timestamps, member count, storage estimate, minimum client version, account email *hashes* and each account's plain email address (stored at sign-in so a returning person can continue with a passkey alone; not shown in the admin view), credential public keys and passkey names, hashed backup-code verifiers, opaque principal IDs with kind/scope/expiry and support invitation marker, an opaque link from an approved agent to its approving person (needed to remove their agents together), and pending invite public keys. The operator can see which email addresses are members of which journeys; request timing can link active accounts. Email delivery exposes destinations to the mail provider.

Encrypted storage: record envelopes, private control labels, person keys sealed separately for each credential and backup code, and age key wraps. Signed public proofs expose only authority fields and label digests. The operator cannot derive the backup codes, PRF results or person keys from these blobs. Ordinary API paths never hold an epoch key or item plaintext; live agent links remain a labelled exception that decrypts only in memory. The Worker cannot prove that a hostile signer encrypted private labels, but those labels never authorize anything. Server and devices verify the signed controls and use compiled Bend rules for authority, current role, inherited agent access and the last-person-guide invariant. A person may leave or remove their own agents; guides may remove other members. Agents cannot change membership or keys. The server can withhold or replay old valid data; clients need their own checkpoint to detect rollback. Registry counters and journey listings may lag after a cross-object interruption; `EnclaveObject` remains authoritative for access. `lastActive` tracks writes, and `storageBytes` estimates stored ciphertext rather than SQLite overhead.

## Artifact commits and retention

Use the existing `POST /log` route for `artifact.create`, `artifact.version`, `artifact.comment` and `artifact.delete`. Send `{control:{proof,envelope}}`, without wraps or admission fields. Signed proofs bind the journey, signer, chain position and encrypted payload. Public fields contain IDs, attribution, type hash and blob descriptors; title, content, tags, filenames, MIME types and comment text stay encrypted. Private content never grants access.

Each new reference must be a completed, unexpired upload owned by that signer in the current journey/epoch. A later writer may retain a committed attachment only from an undeleted version of the same artifact. The journey object serializes operations and atomically commits the proof, derived artifact state and blob references in SQLite. Exact committed-proof retries return 200 with `retry:true`; different or stale replays conflict with 409. Failed commits leave staged bytes, not a partially visible artifact. Uploads cannot overwrite completed bytes. Access changes and rotation can proceed during streaming; upload completion and commit check current authority again.

Every undeleted version keeps its attachments live, even after an edit stops displaying them. A signed tombstone hides all versions/comments and immediately denies new downloads. An alarm retries deletion of expired staged bytes and unreferenced deleted attachments; it never collects a live reference. Signed proofs and encrypted metadata remain as retained history for verification/export, not secure erasure. Already downloaded copies cannot be recalled.

The existing `/a/:secret` overview remains a labelled, read-only server-decryption exception. It shows artifact text, attribution, comments and attachment metadata in bounded pages, excludes recovery records and deleted artifacts, and says attachments require the member interface. There are no link search/show/download routes.

## Project controls and link selectors

Stage 2 uses the same signed `POST /v1/journeys/:id/log` route for `project.create`, `project.purpose`, `project.state`, `project.join`, `project.leave` and `artifact.project`. Send only `{control:{proof,envelope}}`; no wraps, plaintext purpose or caller-supplied projection. The journey object serializes authority checks and atomically stores the proof, Bend-derived project/participation/placement state and chain head. It rechecks current identity, capabilities, epoch, participation and pending rotation before commit. Exact committed proofs return 200 with `retry:true`; changed or stale proofs conflict with 409. Rejections leave storage unchanged.

Creation and placement require ordinary content-write authority. Joining/leaving is person-only and self-only. Participants, including read-only people and agents following their adding person, may edit purpose/state; guide status alone grants neither participation nor content writes. Metadata controls remain available during pending rotation. Projects, including archived projects, organize artifacts but never restrict their readers, downloads or exports. Old histories start with empty project/placement state without migration.

`GET /a/:secret` defaults to main (unassigned artifacts). `?project=main`, `?project=<ULID>` and `?project=all` select main, one project or all undeleted artifacts respectively. Unknown/foreign IDs return 404; malformed selectors return 400. Each response includes `selection`, paged `projects` rows and each artifact's nullable `project`. Project summary rows carry `id`, `purpose`, `state` and `revision`; long purpose text continues with `part:{number,of}`. Participant roster rows carry the same `id`, `participants` and their own `part:{number,of}`. Concatenate purpose fragments and participant arrays in page order. All UTF-8 JSON pages stay within `PAGE_LIMIT` (12,000 bytes); `page.next` preserves the selector. Projects and rosters come from verified replay, not stored plaintext. Links still have no mutation/search/show/download routes, and every request rechecks expiry/revocation. Denied upload request bodies are cancelled before the denial response.

## Local checks and configuration

Run `npm ci` at the root, `npm run build -w packages/core`, then `npm run typecheck -w packages/server` and `npm test -w packages/server`. Tests run in workerd with SQLite objects and a software P-256 passkey authenticator. Email delivery alone is faked at the binding; no Cloudflare API is called. `wrangler.jsonc` declares `REGISTRY`, `ENCLAVES`, `MAGIC_EMAIL` from `noreply@wayfinding.support` with no destination restriction, per-IP and per-email rate-limit bindings plus `AGENT_SESSION_RATE` (ten per IP per 60 seconds), `RP_ID`, `ORIGIN`, the custom domain, and `workers_dev: false`. Provision `EMAIL_HASH_KEY` and `ADMIN_TOKEN` as secrets; neither belongs in the config. `ARTIFACT_BLOBS` binds a private R2 bucket. Test configs bind local R2 only; `npm test -w @ai-wayfinding/server -- test/stage1-storage.test.ts test/stage1-link.test.ts` exercises workerd, SQLite and local R2. `npm test -w @ai-wayfinding/server -- test/stage2-projects.test.ts test/stage2-link.test.ts` additionally proves current project authority, serialized races and Unicode link pagination. No bucket creation, Cloudflare API call or deployment is needed for these checks. Deployment and Cloudflare resources belong to the parent. Open journeys and total storage quotas remain outside this stage.

## Known M2 limits

The server stores `recoveryWrap`, but M2 has no endpoint for a person who has lost every passkey to retrieve it. Keep the matching wrap with the printed recovery identity until a recovery flow exists. Legacy core `delete` records remain append-only; Stage 1 artifact deletion uses the tombstone and blob cleanup policy above. Neither gap gives the operator a decryption key. Control labels may be unavailable without earlier epoch keys; historical wraps for newly added agents remain separate backlog work. All server membership changes and rotations require matching verified signed controls.
