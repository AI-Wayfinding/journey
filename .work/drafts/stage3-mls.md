# Stage 3: MLS, local proxy and personal groups

## Summary <!-- work:summary -->
Add end-to-end encrypted artifact content. A local proxy (`packages/proxy`, a stdio MCP server the person's local agent runs) holds MLS state and keys, talks to the Wayfinding MCP server at `https://poc.wayfinding.support/mcp`, and encrypts and decrypts artifact content. The server relays opaque MLS messages and stores ciphertext blobs; it never sees plaintext content or content keys and runs no MLS library. Each person also has a personal group (their devices and agents only) and can copy or move artifacts between it and a journey.

## Why <!-- work:rationale -->
Design decisions 4 and 6: content is private to members; MLS (RFC 9420) carries per-artifact keys. Library choice: `ts-mls` 1.6.4 (latest stable release, MIT, one dependency `@hpke/core` 1.9.0) with ciphersuite 1 `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`, which needs no extra packages. The npm `openmls-wasm` 0.1.0 is an experimental build from a non-official maintainer, so the design's fallback applies. ts-mls is unaudited and says so; the proxy reports it as unaudited. It sits behind an `MlsGroup` interface so an audited library can replace it. Per-artifact content keys are random AES-256-GCM keys from Web Crypto; artifact ciphertext goes to R2 via the server; the key travels to members as an MLS application message. A member added later receives the keys for artifacts they are entitled to from an existing member's proxy after the add commit. A removed member's proxy cannot decrypt messages after the removal commit, and artifacts created after removal use fresh keys. Copy decrypts in the proxy and re-encrypts under a fresh key in the destination group; move is copy then delete of the source. The proxy signs in with WorkOS AuthKit using OAuth 2.1 with PKCE and a loopback redirect (dynamic client registration is enabled on Staging). The MLS sign-in-page client is out of scope here (stage 4). Hard constraints: core code uses Web Crypto and no `node:` imports outside the CLI entry; exact pins; values below 2^53; no real confidential data.

## Acceptance criteria <!-- work:criteria -->
- mls-group: An `MlsGroup` interface backed by ts-mls 1.6.4 creates a group, adds and removes members by key package, and seals and opens application messages; a member added later can open messages sent to it after joining, a removed member cannot open messages sent after its removal, and the implementation reports itself as unaudited.
- mls-relay: The MCP server offers tools to publish and fetch key packages and to post and fetch MLS handshake and application messages per journey or personal group in epoch order, and to put and get artifact ciphertext blobs; only live members can post or fetch, refusals leave state unchanged, and the server stores these as opaque bytes and imports no MLS library.
- mls-proxy: With two members on separate proxies against the server, an artifact created by one is readable by the other, a member added later reads entitled history, a removed member cannot read content created after removal, an artifact in a person's personal group is unreadable to every other member and to the server, a copy or move into a journey makes it readable to that journey's members and a move leaves no readable source, and the server's stored data contains no plaintext content or content key.
