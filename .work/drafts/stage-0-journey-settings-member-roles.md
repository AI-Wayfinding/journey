# Stage 0: journey settings and member roles

## Summary <!-- work:summary -->
Deliver a Bend rules core first, then Stage 0 journey settings, read-only/read-write roles, person guides, inherited agent access, personal controls and consistent removal. Require clients 0.1.3 and older to update; align browser, CLI/MCP and links. This is a draft plan, not implementation approval or passing evidence.

## Why <!-- work:rationale -->
Decision 0001 D5, D7, D30, D32–D34, D40–D41 and ontology sections 9–10 define this stage. Amendments D31–D44 override earlier decisions. The ontology's approval remains a prerequisite to implementation; promoting this draft does not establish that approval. Keep the stage independently shippable and preserve existing encrypted text, history, recovery/export and deliberate live agent-link behavior.

Dan approved Bend for the rules core. Keep pure Stage 0 decisions in one `packages/rules/` folder, with `LAWS.bend` and `PROOF.bend` at that package root. Compile the implementation to `rules.mjs`, shared by core, server, web and client. TypeScript parses and verifies signatures, binds controls to ciphertext and chain position, copies named fields and performs storage/cryptography/transport; only already-verified entries cross into Bend for authority decisions and membership replay. No duplicate decision rules remain in TypeScript. The symbolic key-holding law models recipients after removal and rotation; it does not prove cryptography or erase previously downloaded keys. Later stages add their own laws, not speculative Stage 1–7 rules now.

Content role and guide authority are different: a person guide may have either role, and an agent cannot be a guide. A hostile or careless caller must not turn guide authority or a personal control into a content write, act as another person's profile, elevate an agent beyond its adding person's current access or its original read-only/read-write limit, or leave a journey without a person guide. A plain access row supplied by a caller is not proof of authority. Removed people and their agents must lose future records and keys; already downloaded keys and copies cannot be recalled. Pending rotation must block content writes and reservations while allowing authorized controls needed to complete it.

Settings in this stage cover editing the journey name/description and default new-person content role under guide authority, plus durable visibility type and joining-policy representation. Retain private-only journey creation and the existing invite-based admission flow. Store that flow honestly as invitation-only; do not offer immediate joining or unrestricted request admission, claim those policies work, or implement their key delivery. Represent the three D41 policies for later activation without implementing Stage 6. Default role must govern normal admissions now; existing temporary support admissions must not silently become writable or permanent. Visibility is stored separately from today's sealed transport so conversion can be added later, but cannot be changed in this release. Listing storage/discovery and public creation are Stage 6, not settings to advertise as active here.

Out of scope: artifacts/files and item migration (Stage 1); projects and agents following people into projects (Stage 2, D35); private artifacts and interview-subject access (Stages 3–4, D44); rounds, HTML/applets; public journeys, listing, full joining policies, copying and conversion (Stage 6); shared read refactoring/parity and drops (Stage 7). D43's new public/journeys-only member visibility setting, profile-picture field and public attribution are not assigned to Stage 0 by ontology section 9 and are deferred with the public-journey work. This stage keeps the existing self-managed display name and journey email opt-in; it does not invent picture storage or remove legacy email behavior. Account deletion, general security hardening, historical wraps for newly added agents, recovery/key-persistence discrepancies and a second security review remain the separate backlog.

## Verified source observations

Read both source documents in full and inspected the code cited below. These are observations of the current tree, not security certification or instructions to preserve defects.

- `packages/core/src/log.ts` defines `members.manage`, person-only control signers and a last-person-guide check. People normally have no explicit content scope; support people use `read`. Agent scopes are independent. Genesis accepts only sealed/private; there are no settings or general role-change entries. `member.profile` is self-only name plus optional email. Core permits self and own-agent removal.
- `packages/core/src/removal.ts` requires a guide for its remove-and-rotate helper and rejects self-removal. `packages/web/src/journey.ts` uses that helper and supplies encrypted entries plus plain `accessChanges`; `letIn` uses readwrite for normal people. Browser `saveRecord` checks scope but not minimum client version.
- `packages/server/src/enclave.ts` stores encrypted log entries and plain principal scopes without verifying signed control history. `access` does not consult an agent's adding person. `logWrite`, `renew` and invitation access require readwrite; direct agent removal requires its adding person, even when a guide could authorize it in core. Removal sets pending rotation, cascades a person's agents, and blocks reserve/recordWrite while leaving log writes available to readwrite principals.
- `packages/server/src/index.ts` validates/copies transport fields, obtains account identity for admitted people from pending requests, and routes agent additions through approval. It passes plain changes to the enclave. Invite creation/pending lookup use the enclave's scope-only check. Live link creation/renewal use fresh person confirmation and link reads go through enclave access.
- `packages/web/src/main.ts` skips name propagation for read-only journeys, disables their email choice, hides link-agent creation for them and shows remove buttons only for guides. Leaving is a separate self-removal path. Its share heading says “Share this journey with other wayfinders”.
- `packages/core/src/versions.ts` has `CLIENT_VERSION = '0.1.3'`. `packages/client/src/journey.ts` and `packages/server/src/agentLink.ts` check minimum versions on verified reads. Client writes/status use only the agent's own scope. The web journey helper has no minimum-version gate. D30 therefore requires an update gate, not a promise that old clients understand new entries.
- `packages/core/test/log.test.ts` and `packages/core/test/flow.test.ts` cover signed-history checks and rotation; server tests use the Cloudflare Vitest pool; browser unit tests use Vitest; browser end-to-end tests use Playwright with a local Wrangler server; client integration tests use local workerd. Package scripts/configuration were read before specifying evidence commands.

## Worker boundaries

### bend-core

Run `bend guide` with Bend on PATH before writing Bend. Use the working `.scratch/bend-spike/` as a read reference, not a complete Stage 0 model: its single law is only a starting example. `import ./access.bend as A` imports implementation definitions; `PROOF.bend` must import `./LAWS.bend as Laws`. The compiled `.mjs` default export exposes non-IO definitions; JavaScript constructors use `{$: "Name"}`.

First compile a minimal pure rules module and run actual calls in the server's Cloudflare Workers Vitest pool (workerd), then Node and the browser test runtime. If workerd fails, stop this node and report the failure to Dan before continuing; the worker must not choose a fallback or duplicate TypeScript implementation. This first compatibility check precedes the full rules port and downstream nodes.

Keep role/content access, person-guide and settings authority, exact D34 agent access, removal/leaving and replay of already-verified control entries as pure Bend functions. Agent access has only the member's current role and the read-only/read-write setting at addition as its role inputs; missing/removed/expired membership is a liveness check, not another independent role grant. Preserve the last person guide and cascade person removal to their agents. Removal authority remains distinct from guide-only key rotation. Accept verified normalized data, not unchecked signed bytes or caller-supplied access rows. Model key holdings symbolically by principal and epoch: removal plus rotation excludes the removed person and their agents from the new epoch; old epoch keys remain outside that guarantee.

State the six minimum laws in `packages/rules/LAWS.bend`: an agent never exceeds its member; agents are never guides; only person guides change settings/roles; the last person guide cannot be removed (including leaving or losing guide authority); removing a person removes their agents; removal and rotation leave removed people and their agents holding no new-epoch key. Also cover replay and removal/leaving transitions used by Stage 0, not just fixed examples. `PROOF.bend` proves the laws against the same pure functions compiled for production. Run `bend PROOF.bend` and `bend PROOF.bend --verdict`; both must print `ALL PROOFS CHECK`. No unsafe or foreign-code shortcut may stand in for a proof. Laws describe the approved decisions; changing a law's meaning requires Dan's approval.

Add rules compilation to the root and consuming package build scripts so clean builds produce `packages/rules/rules.mjs` before imports resolve. Reuse that one module through thin TypeScript adapters and imports in core/server/web/client; adapters may translate named fields but must not reimplement the decisions. Replace current in-scope TypeScript rules with calls into it and keep existing behavior tests passing. The later protocol node wires new signed entry formats and verified projections into those rules. Shared package/test/config paths are deliberately serialized by dependencies; do not implement the later nodes here.

As part of this node, add these four guide-derived lines to the repository-root `AGENTS.md` (do not edit it while merely revising this plan):
- Run `bend guide` before writing Bend code.

### protocol

Depend on `bend-core`. Choose the smallest versioned signed records and TypeScript adapters to the Bend permission functions needed for this stage. Document their server-verifiable authority projection and legacy upgrade procedure without exposing private profile/content plaintext. Plan later-stage record/version boundaries in the protocol document, not unused implementations. Existing history cannot be rewritten or trusted through caller-supplied access rows. Settings represent the active private/invitation-only stage and the three future joining values, not working Stage 6 flows. Preserve support read-only expiry during migration without making it an unrelated permanent privilege model. ### server-authority

Use the compiled Bend rules through the protocol adapters for authority, current access and verified membership replay; do not recreate the decisions in TypeScript. Implement the protocol's verified authority projection, durable settings and safe legacy bootstrap in the enclave and routes. The server must not decrypt ordinary private content or profiles to authorize a control. Creation and migration trust must be established, not inferred from today's writable principal rows; replay/order and ciphertext/projection binding are part of this stage, not the broader rollback/checkpoint backlog. Use current trusted state and transactional checks so two individually permitted removals cannot jointly remove all guides and stale additions/roles cannot overwrite newer authority. Copy named caller fields. Re-evaluate effective access for every records/log/wraps/export/reserve/write route and for link-owned agents, not just session approval. Distinguish content, personal and guide operations; allow read-only guides to rotate while pending. Apply signed default roles during existing admission, with support expiry preserved. Keep invitation-only operation; forbid activating other policies and changing visibility. Bind plain row updates to the verified change or derive them; reject mismatches before any storage, registry membership or link changes. Ensure no successful response exposes a partially committed grant/removal. Keep fresh passkey confirmation and current agent/link expiry behavior. Test direct malicious calls, forged proof/extra fields, mixed batches, conflicts, downgrade after reservation, cascade and resumed rotation; demonstrate the negative control tests fail with the relevant check removed in a disposable tree.

## Acceptance criteria <!-- work:criteria -->
- bend-runtime: Before porting the full rules or starting downstream nodes, the same compiled pure Bend module executes representative rule calls in the server Cloudflare Workers test runtime (workerd), Node and the browser test runtime; a workerd failure stops the node and is reported to Dan without a worker-selected fallback.
- bend-build: When a clean repository build runs, build scripts compile the single packages/rules source folder to rules.mjs before core/server/web/client consumers resolve it, and those consumers import that shared default-export module rather than independent rule implementations.
- bend-laws: When packages/rules/PROOF.bend is checked against root LAWS.bend and the production pure functions, both bend PROOF.bend and bend PROOF.bend --verdict print ALL PROOFS CHECK for laws that agents never exceed their members or become guides, only person guides change settings/roles, the last person guide survives removal/leaving/guide changes, person removal removes their agents, and removal plus rotation leaves the removed person and their agents with no key for the new epoch in a symbolic key-holding model; the model also covers Stage 0 verified-control replay and does not claim a cryptographic proof or recall of old keys.
- bend-ts-integration: When existing TypeScript behavior suites run with in-scope rule code replaced by calls into the compiled Bend module, they pass across core/server/web/client, and source checks reject duplicate role, guide/settings authority, D34 access, removal/leaving or membership-replay decision implementations in TypeScript while allowing parsing, signature verification, named-field adapters and effects.
- bend-agent-guidance: When the Bend core is delivered, repository-root AGENTS.md includes four guide-derived instructions to run bend guide before writing Bend, keep rules in packages/rules/LAWS.bend, run bend PROOF.bend from packages/rules before committing, and parallelize independent work where possible.
- settings-records: When a guide edits the journey name, description or default new-person role, signed replay retains the change and supplies the default role for normal admissions; the Stage 0 model retains private visibility and invitation-only joining separately from transport and validates all three D41 policy values for later use, without enabling visibility conversion or later-stage policy activation.
- role-authority: When signed controls are replayed, only person guides of either content role can change settings, person roles or guide authority; agents never receive guide authority; read-only people can change only their own existing profile, add/name/manage their own agents and leave; a guide cannot impersonate another profile, obtain content writes from guide authority or remove the last person guide, and visibility type cannot be changed.
- agent-access-model: When either person role changes, every agent's effective access is the adding person's current access limited only by the read-only/read-write choice made at addition; a read-only agent never gains writes, a read-write agent cannot write while its person is read-only, and missing, removed or expired adding people give no live access; agent links remain read-only and no independent agent grants or scopes can widen this rule.
- removal-model: When a person of either role removes their own agent, a guide removes another member or agent, or a person leaves, the common removal model permits exactly those actors, removes a person's agents, retains at least one person guide, and separates removal authority from guide-only rotation so a non-guide removal can hand rotation to a remaining guide without granting management authority.
- legacy-upgrade: When a legacy journey is upgraded, original signed entries and encrypted content remain readable to the upgraded reader, normal people retain their prior writable role, support people retain read-only expiry, person guides and each agent's original limit remain intact, missing settings reflect existing private invite-based behavior, and a guide raises the minimum above 0.1.3 before any new incompatible control entry without permitting a later minimum decrease or silent privilege expansion.
- verified-server-controls: When a caller submits creation, settings, membership, role, guide, renewal or rotation changes, the server verifies the actor, signature, journey, chain position and authority against current trusted state before committing, projects signed settings durably and applies the default role to normal admissions without widening temporary support access; forged, replayed, cross-journey, stale/concurrent or mismatched plain access changes are rejected without partial durable changes, and unnamed caller fields do not survive into signed authority or storage.
- server-content-access: When a caller reads records, history, wraps or export, reserves a sequence or submits any ordinary content write including comments or deletes, server access reflects the current verified person role and exact D34 agent rule; read-only callers including guides cannot write, role downgrade also stops an earlier reservation from completing, missing/removed/expired people and their agents cannot fetch new data, and promotion of a person never promotes an agent beyond its original limit.
- server-personal-controls: When a read-only person uses profile updates, own-agent approval/naming/link creation/renewal/removal or leaving, the server allows the authorized personal control with existing fresh-confirmation requirements, while denying other people's controls; either-role person guides can use settings, role, guide and existing invitation/admission controls, while non-guides and agents cannot use those management routes and no control permits an ordinary content write.
- server-removal-rotation: When an authorized own-agent removal, guide removal or self-leave commits, the server revokes the target and a removed person's agents and links immediately, protects the last person guide, sets pending rotation and refuses new reservations and all content writes including already reserved ones until rotation completes; authorized control writes remain possible and a remaining read-only or read-write guide can resume interrupted rotation with exactly the remaining recipients and next epoch, while removed principals receive no new wraps.
- server-version-gate: When a client at 0.1.3 or older, or a direct caller lacking required format capability, reaches an upgraded journey, the server enforces the update requirement before returning ordinary content or accepting writes/controls; capability claims never replace signature/authority checks, unsupported controls fail closed, and enough non-content information is available to explain the required update.
- browser-controls: When a person reloads after settings, role or guide changes, the browser shows current signed settings, read-only/read-write role and guide authority separately; guides of either role can edit name/description/default role and manage members, read-only people can save their own name and existing email choice, add/name/remove their own agents, create/renew their read-only links and leave, non-guides cannot manage others, last-guide actions are refused, content controls follow role, and the share heading says “Share this journey with other people” rather than “other wayfinders”.
- client-effective-access: When the adding person's role is downgraded and later restored in a real local journey, both CLI and MCP writes and status use current verified effective access rather than remembered approval scope; read-write agents lose writes during downgrade, read-only agents never gain them, both retain allowed reads, and removal of the adding person ends their access.
- interface-update-gates: When browser, CLI, MCP or live agent-link readers encounter an upgraded minimum or unsupported control type, they fail closed with a clear update message rather than rendering partial content, writing through a stale context or suggesting approval again; upgraded readers still read legacy history, and links remain read-only without adding Stage 7 parity features.
- stage0-regression: When the completed Stage 0 tree is built and tested from the repository root, all package typechecks and builds, core Node/workerd/browser tests, server tests, web unit/end-to-end tests and client unit/integration tests pass, including the new Stage 0 negative authority and migration cases.
