# Stage 3: private artifacts

## Summary <!-- work:summary -->
Deliver author-private artifacts and private cross-journey copies without publishing their content, metadata or existence. Store their signed history, encrypted content, search index and attachments together in one padded, encrypted vault per member on the journey server, separate from shared journey storage. Fixed size buckets conceal private artifact counts; the client checks a monotonic signed vault version to detect rollback. The member's existing keys unlock the same vault on multiple devices. Support browser and CLI/MCP workflows and explicit encrypted handoff to the author's eligible agents. Private copies keep their author and privacy in either destination visibility. Agent links never receive private material or private counts. Preserve Stage 0–2 controls, projects, journey-visible artifacts and viewers. This is an implementation plan, not implementation approval or passing evidence.

## Why <!-- work:rationale -->
Ontology section 9 Stage 3, section 6's private-artifact/copy/project/access rows and decision 0001 D5, D10–D11, D14–D15 as amended by D31, D34–D36 and D38 define the outcome. D30 defines update behavior. D43 forbids naming a private source publicly; D44 reserves the interview-subject exception for Stage 4. Amendments override earlier wording: D15's visible size/date/authorship and named-person sharing are not allowed. Projects organize copies; they do not confer access. Main at 889b218 is the inspected baseline, with Stage 0/1 implemented. Stage 2 is an external prerequisite: assume .work/drafts/stage-2-projects.md lands with its exact project-v1 records, placement/selector rules and client 0.1.6. Do not build against an imagined alternative Stage 2 implementation. Ontology approval remains the implementation prerequisite; draft promotion grants none.

A hostile or careless caller must not disclose a private artifact's existence, IDs, title, type, author, size, date, versions, comments, attachments, origin, placement or counts to another member, guide, facilitator, link holder, public reader or server operator. Eligible authenticated agents receive only their derived D34 audience, never access merely from knowing a vault handle. They must not use a journey key, recovery recipient, link credential, foreign agent, project membership, fabricated author binding, stale predecessor, unsigned index or public destination to gain that audience. They must not cause private bytes or even private reference markers to enter shared journey proofs, records, wraps, blob/R2 paths, logs, analytics, error reports, journey exports or agent-link pagination. The dedicated vault store contains only padded ciphertext; its handles, sizes, access patterns and version transport must not disclose whether any private artifact exists. A stale server response must not roll a client back below its verified signed vault version or resurrect a deleted copy. They must not turn an author-private copy into an ordinary shared copy by changing flags, publish its origin, grant direct recipients, exceed D34, resurrect deletion or smuggle extra fields into stored/output objects.

All audience, access, inheritance, lifecycle, copy/placement and version decisions belong in production Bend functions in packages/rules, with LAWS.bend and proofs of the actual functions in PROOF.bend. TypeScript validates exact formats, cryptographic signatures, authenticated ciphertext and key/identity bindings; it copies named fields, encrypts and stores, and projects Bend results. Extend scripts/check-bend-boundary.mjs without weakening previous stages. Existing public ControlProof remains the only authority for journey membership/settings/projects/shared artifacts. Private actions have one separate encrypted, signed vault history; there is no public private-artifact action and no competing membership authority.

Out of scope: anonymous/public journey creation or reads, listing/joining/conversion activation and ordinary shared-copy publication (Stage 6); rounds, interview types/labels and D44 subject access (Stage 4); HTML/applets (Stage 5); full shared-read parity and drops (Stage 7). No private-to-shared visibility conversion, direct recipient grants, general account recovery redesign or security certification. Server-backed multi-device vault access, fixed-bucket padding, existence-secrecy transport and signed-version rollback detection are in scope. Bucket policy, traffic concealment and new-device freshness need the technical decisions below; they are not grounds to weaken D36. Preserve header/footer, approval-first connection and existing artifact/viewer limits. No deployment, provisioning, package publication, real Keychain/journey access or remote action is evidence.

## Decisions taken

The recorded operator storage decision overrides the earlier device-local design. These choices need lead review; unresolved technical details are marked below, not another open product question about storage location.

1. **Server vault with mandatory existence secrecy:** use one encrypted vault per member, not one object per artifact, copy, journey, attachment or device. The journey server persists only padded ciphertext in a dedicated vault store, never plaintext indexes, descriptors, keys or private actions. The same member vault holds its private copies across journeys. Do not reuse /log, /records, /wraps, shared blob/R2 or archive paths: their sequences, descriptors and counts leak private activity. Provision an indistinguishable encrypted empty vault for members with no private artifacts; the presence of a vault cannot signal a private artifact. Pad the complete vault, including history, indexes, attachments and key wraps, to fixed size buckets before encrypting it, with fresh randomness/nonces on replacement. Bucket lengths, transitions, reads, writes, retries and polling must not reveal private artifact count or existence to members, links or the operator. Encryption and padding alone do not conceal access timing or growth. The exact bucket/traffic policy is an open implementation-blocking decision below; tests must establish D36 rather than assume it. A server delivering malicious executable application code or a compromised device/authorized agent remains outside the cryptographic trust boundary, not ordinary server storage, logging or traffic observation.
2. **Keys, versions and multi-device durability:** generate a random 256-bit vault root per stable member/author and independent random 256-bit keys per private copy. Age-wrap the root only to that member's existing pinned recipient; their existing signing key signs vault updates. The same existing keys unlock the server vault on another device; there is no device-specific authoritative vault, new identity or journey/recovery-key fallback. Use Web Crypto AES-GCM with fresh 12-byte nonces and HKDF-SHA256 domain separation: salt is UTF-8 `wayfinding/private/v1`, info is canonical JSON `{purpose, vault, copy}` where purpose is exactly vault, history, index, copy-wrap or blob and copy is null for vault/index/copy-wrap keys. Authenticate format, vault ID, author identity, copy ID, record ID and vault revision as applicable. Derive history/blob keys from the copy key and vault/index/copy-wrap keys from the root. Never reuse journey envelope/blob constructors. Copy-key wraps, histories, indexes and blobs stay inside the root-encrypted contents. Deliver the age-wrapped root in the same padded ciphertext container, in a framing layer the member can open with their existing age identity before unlocking those contents; no separate per-copy wrap endpoint or plaintext root-delivery metadata. Empty/populated vaults use indistinguishable framing. Agents receive only scoped copy keys in individually age-encrypted handoff bundles, never another author's root or index key. Every vault replacement contains an authenticated member-signed manifest binding vault/author, monotonic safe-integer version, previous signed-head hash and complete contents digest. Clients verify that signature, chain and digest before rendering or accepting state; reject lower versions, conflicting same-version heads, missing predecessors and unsigned replacements against a retained highest verified checkpoint. Persist the checkpoint independently of replaceable cache bytes and advance it only after verified commit. Server replacement uses an opaque compare-and-swap token (a token that rejects writes based on an outdated vault) for atomic whole-blob updates, never last-write-wins; it is not trusted freshness evidence. Version/checkpoint transport must not expose private-operation counts. New-device checkpoint bootstrapping and fork detection need the decision below; a valid signature alone cannot establish freshness. Local IndexedDB/Node stores are encrypted caches/staging, not the only durable copy: use atomic transactions or 0700 directories/0600 files, atomic rename and exclusive writer locks. Clear plaintext indexes/previews, cancel workers and revoke object URLs at lock/sign-out/context change. Reload/fetch verifies the signed vault and checkpoint before rendering; corrupt, stale or unavailable storage is not an empty vault. Explicit encrypted backup/import remains available, but losing a cache does not lose server-backed artifacts; losing existing member keys follows existing key-recovery limits, with no new general recovery promise.
3. **Stable author and actual actor:** immutable author identity is `{kind, signingKey, recipient}`, pinned by the creating member in a verified journey genesis/member.add history and by that member's signature on the first private record. Store journey-scoped principal bindings separately as `{journey, principal, admissionHash}` inside the encrypted vault. Bind both public keys and member kind, not email, display name, server account ID or a matching principal string. The same person can have different principal IDs in different journeys. Re-admission requires a fresh verified binding, not revival of old participation. Each private version/comment names its actual actor/signing key separately from its immutable author. A person-created artifact belongs to that person; an agent-created artifact keeps the agent as author under D38. Do not silently rewrite an agent author as its adding person. An agent author's author-only audience is that agent (agents cannot add agents); its adding person's access limits its operations under D34 but does not itself grant read access to the agent's private vault. A matching signing key alone, changed recipients, key substitution, borrowed principal IDs or caller-supplied author objects do not establish continuity; matching both keys/kind plus independently verified admission and author signatures is required. Key rotation/author transfer is not offered in this stage; changing identity needs a future explicit protocol, not a forged copy origin.
4. **Audience and agent delivery:** for a person author, the audience is that person and currently live authenticated agents added by that person in the copy's containing journey, subject to the adding person's current membership/access and the agent's original limit. Read-only agents may read, never write. Agents from other people or other journeys do not gain access through a common vault; exported agent bundles contain only copies in journeys where that agent is currently eligible. Agent links are always excluded, including links added by the author: their identity is intentionally recoverable by the server. Explicitly distinguish verified link credentials from authenticated CLI/MCP credentials; a missing or unverified credential class fails closed, not a default authenticated classification. Before each first handoff/admission binding, use an author-generated 32-byte random local challenge and require an Ed25519 signature by the admitted agent key over canonical `{format:'private-v1',purpose:'handoff',author,journey,principal,admissionHash,recipient,challenge}` plus successful opening/return of an age-encrypted challenge to its admitted recipient. Transfer these challenge files locally, never via the journey service; consume the challenge once. Require both verified member admission and both private-key possession proofs. Server credential-class metadata is only a negative hint and cannot grant audience or substitute for these proofs. Link creation discards its Ed25519 private key and never produces this local authorization; the server's possession of the link age identity alone cannot pass. An approved agent must protect its keys; a deliberately malicious authorized agent remains outside the guarantee. Private-key wraps are never included in member.add, approvals, link blobs or shared server responses. Only the member's dedicated padded vault response carries its encrypted author/copy wraps; it never exposes them separately or delivers an author root to another agent. The author explicitly exports a scoped age-encrypted handoff file and the authenticated agent imports it locally. This is key delivery to the already-derived author audience, not a named-recipient sharing feature: UI/CLI accept an eligible agent ID, never an arbitrary recipient or grants array. Agent-produced updates are signed encrypted return bundles that the author imports and re-verifies; no automatic server relay. Multiple devices update the same member vault through signed-version checks and atomic replacement; agents still exchange scoped bundles. Divergent vault or copy predecessors conflict, never last-write-wins. New eligible agents receive history only through fresh explicit author handoff. No hidden background key delivery is claimed.
5. **Current access and downloaded-copy limit:** already downloaded material/keys cannot be revoked. The server authenticates the member for the opaque vault transport, never inspects private content or derives artifact authority. It must not expose another member's vault or hand an author root to an eligible agent. Clients verify ordinary journey membership/project history and current expiry through Bend before private mutations, copy/placement and handoffs, and recheck cited heads before accepting agent returns or imports. When required authority is unavailable or known stale, deny new mutations/handoffs until ordinary journey refresh completes. Offline access is read-only to already verified cached copies, with freshness explicitly unconfirmed; no offline proposal is silently committed on reconnect. Online writes fetch/verify the current signed vault version and ordinary authority, then atomically replace the ciphertext using the observed vault token; conflict requires refresh/reverification. Removal/expiry/downgrade detected before commit aborts it. This opaque server commit serializes vault replacements, not hidden artifact permissions or changes concurrent with an undetected remote control. Stop future handoffs and update acceptance after removal/expiry; do not imply keys can recall old copies. Historical backup recovery is read-only until live authority and a trusted vault checkpoint are available; importing an older backup cannot lower the signed version or resurrect deletion. Guide/facilitator status grants nothing. Private mutations/copy/placement require ordinary content-write authority; D17 is not private-write authority. Pending journey rotation blocks those mutations, not already-received reads.
6. **One encrypted private action format:** introduce `PrivateRecord` with exact `{format:'private-v1',v:1,id,vault,copy,seq,prev,at,actor,authority,type,body,payloadHash,sig}` entirely inside copy-key encryption. `id` is a fresh ULID and the idempotency operation ID; vault/copy IDs are random 256-bit base64url values without time bits. `seq` is a safe nonnegative integer scoped to each copy's chain; its first create/copy record is zero with null prev, later prev is SHA-256 of canonical complete signed record. Separate copy chains allow an agent to verify its complete eligible history without exposing other copies or even omitted-record counts. The encrypted vault manifest is a signed, versioned container whose search/placement indexes are rebuilt from verified per-copy history, not a competing membership authority. Its version/head binds atomic server replacements and client rollback checks; it does not expose an artifact count. Ed25519 signs canonical JSON omitting only sig. `authority` pins containing journey, actor principal, verified journey proof head/hash and epoch; accepting code verifies the complete supporting ControlProof history and keys independently. The first create/copy record pins author; supported action strings are `private.create`, `private.version`, `private.comment`, `private.delete`, `private.copy`, `private.project`. Copy records describe content/provenance, never membership changes. Each body copies exact named fields: every body has artifact (fresh random 256-bit base64url stable ID at first create), immutable author identity and actual actor key identity; containing copy comes only from the signed top-level copy field. Create/version add version (fresh ULID), typeHash, blobs and predecessor (null only at creation). Comment adds comment (fresh ULID) and optional onVersion. Delete adds predecessor equal to the current content head. Project adds nullable project and placement predecessor (null initially). Copy adds origin, destination, snapshotHash, version, typeHash, blobs and predecessor:null; it begins a new destination chain. No other optional fields are allowed. All discriminated schemas reject unknown fields, recipients/grants and unsupported types/versions. The payload is the existing strict Stage 1 artifact content/comment/tombstone schema, encrypted with the copy key, with hashes and descriptors verified after decryption. Private history is the sole action for private content; payloads cannot add actors, commands or access. No private record or hash is appended to public ControlProof. Supporting authority snapshots are encrypted in the vault, not another public chain. Replay uses production Bend and fails before returning a partial view.
7. **Copy/provenance and independent lifecycle:** `private.copy` creates a fresh random copy ID and fresh copy key in a different journey; private artifact identity and author remain stable. Its encrypted origin is exactly `{journey,copy,artifact,version,recordHash}` and destination is `{journey,copy}` with a snapshot hash of the source current version and its attachments. Validate source existence, undeleted head, author identity, actor eligibility and live ordinary write authority in both source and destination, plus destination author membership binding and required versions/capabilities. Agent acting for a person author must be that person's eligible authenticated agent in both journeys; same-key agents require separately approved verified admission/session bindings in each, not reuse of a one-journey session. Copy is a one-time snapshot, not a synchronized alias: future versions, comments, deletion and placement are independent. Copy the selected current version and attachments, not source comments or all historical versions; origin still identifies the exact source version. Re-encrypt every attachment with fresh destination copy/blob IDs/nonces; no source storage handles, ciphertext deduplication, public foreign descriptors or journey-key wraps are reused. Copy records live only in the author vault. An exact record-ID retry is idempotent; a changed body under that ID or origin.recordHash not matching the observed source head conflicts. Destination copy creation requires a fresh unused copy ID and predecessor:null; later destination edits use that copy's own observed predecessor. A private copy always remains private, including in a public destination; no public-origin/name/profile output is produced. Creating a private artifact in the same journey is create, not a fake cross-journey copy. Private-to-shared conversion/publication and shared-to-private retroactive concealment are not offered; Stage 6 owns ordinary shared copies.
8. **Stage 2 placement dependency:** each destination private copy starts unassigned and has zero-or-one nullable project pointer. `private.project` is an action inside the encrypted member vault, not Stage 2's public `artifact.project`, which would leak artifact/author/placement existence. It consumes verified Stage 2 project.create/purpose/state/participation history and uses the same project existence, same-journey, placement-predecessor, undeleted-copy and main/project/all selector semantics. Projects are not privacy boundaries: no participant or guide gains a private key/count. D17 does not authorize placement. Assignment after successful copy/create is separate; do not promise grouped network/local atomic creation. Independent destination project pointers never reference the source project's ID. Archived projects remain selectable/readable; a foreign, absent, multiple, stale or no-op placement fails. Stage 2 project navigation counts must be viewer-scoped: public/link/journey-shared counts use only shared artifacts; the author's authorized view may add a private count after audience selection; that count stays in client memory or inside the padded encrypted vault, never in shared state or transport metadata. Histories without private records have no private indexes and no change to shared placement.
9. **Versions, comments, indexes and attachments:** preserve fixed type, immutable author, fresh version/comment IDs, whole-artifact comments with optional same-copy version context, 1,048,576-byte decoded payload cap, at most eight attachments/version and 25,000,000 raw bytes/file inclusive (zero valid). Private attachment descriptors and dates/sizes/filenames/MIME/path labels are inside encryption; private binary AAD binds vault/copy/blob/key generation/raw size. Copy-key generation is separate from journey epochs. Enforce exact raw/ciphertext lengths, fresh nonces and digest/AAD checks, no cross-copy reference reuse, unfinished stages, unknown fields or paths. Use encrypted client staging and reference accounting inside the vault; commit content/head/index/live references and signed version atomically as one padded server replacement, retain every undeleted version's attachment references, clean abandoned stages after one hour and retry crashes without deleting live bytes. Whole-copy tombstone is irreversible, hides its versions/comments/attachments in ordinary views and removes only its unreferenced bytes; other copies survive. Retain encrypted signed tombstoned history in explicitly labelled private backup, not secure erasure. Rebuild indexes from verified history, never trust imported indexes. Search/filter/list/show/count/versions/comments/download and project selectors select the audience before decrypting/rendering and include no placeholder for unauthorized copies. Missing keys, malformed private records or bad hashes fail the private view, never fall back to journey-key decryption or partial plaintext. Shared views still work independently; a corrupt or rolled-back vault is not silently treated as an empty vault.
10. **Exports and backups:** keep Stage 1/2 `artifact-v1` journey archives exactly journey-visible; never automatically merge private records, keys, blobs, counts or index fields into them, even for their author or an author's recovery recipient. Add separate `private-v1` version-1 age-encrypted bundles: `{format,version,vault,author,scope,authorityHistories,records,payloads,copyKeys,blobs,unavailableDeletedBlobs}` projected by named fields, with exactly one validated descriptor/ciphertext per live reference. copyKeys are exactly `{copy,key}` entries protected by the outer age encryption; never include the author root/index key. Records/payloads include complete per-copy chains only for the eligible selected copies. On author import, rewrap accepted copy keys under the member's vault root and commit them inside a newer padded server vault. On scoped agent import, rewrap accepted copy keys under that agent's independent encrypted cache key; an agent cache is not another author's root replica. `scope` is author-backup, agent-handoff or agent-return; audience/authority checks, not that string alone, determine acceptance. Author backups encrypt to the author's pinned recipient only; agent handoffs encrypt only to a validated eligible agent and include only its permitted copies. No arbitrary additional backup recipients or journey recovery keys. Import verifies pinned author/vault, signatures, complete per-copy chains, membership proofs, current bindings for new proposals, descriptors, decrypted payload hashes and complete live bytes before an atomic signed-version vault replacement (or a scoped agent-cache transaction). Read-only historical author-backup recovery does not require live membership, but cannot accept new proposals or deliver keys until current authority is available. Existing exact history is idempotent; conflicting histories fail without mutation. No plaintext bundle import or private-action replay route on the server: clients verify imports and send only the resulting padded vault ciphertext through the dedicated adapter. Export returns no plaintext keys/content to stdout and never accepts automatic remote paths. Backup/import is optional for the server-backed vault, not the sole durability path. An author import merges only verified nonconflicting history into a newer signed vault version; it never overwrites the current checkpoint with an older backup or resurrects tombstones. Agents retain independent encrypted scoped caches. Server unavailability may prevent online access/commit; rollback below a trusted checkpoint must be detected, not described as an availability limitation.
11. **Public destination checks without Stage 6 activation:** use the same private audience/storage/copy/placement implementation with a verified destination descriptor whose visibility can be private or public. Neither value changes author-private encryption. Portable tests supply public destination state at the verified-model adapter boundary; server tests prove private input to existing public/shared routes is rejected and no new public creation/join/read route is activated. Label these as public-destination privacy contract tests, not shipped public journeys. The runtime destination picker shows only currently admitted supported journeys returned by ordinary verified APIs, presently private. Stage 6 must reuse this private-v1 contract when genuine public histories can be created; its source-name suppression follows D43. Do not temporarily permit visibility:public genesis/settings on main merely to obtain a fixture. Tests cover public descriptors, public/link project counts and public-origin omission, with the same padded server-vault and existence-secrecy contract for both visibility values; destination write/membership denial is tested for both. D44's future subject exception requires a separate signed round relationship/key-delivery design, not a generic recipients field left open here.
12. **Agent-link exclusion and server guards:** links never load an author vault, private key wrap or agent handoff, even when owned by the author. Use an explicit Bend audience result before ordinary shared link rendering/counting/pagination, and require shared-only serializers rather than post-render filtering. Keep Stage 2 main/project/all pages, PAGE_LIMIT, continuation text, Unicode handling, selector-preserving next URLs, no-store, expiry/revocation and recovery exclusion. Private titles/IDs/author/date/size/type/origin/blob notices/counts must be absent from bodies, headers, ETags, errors and next/page counts. A journey with zero shared artifacts and any number of private copies in the padded member vault yields the same link bytes and page structure as one without them. Unknown private IDs are indistinguishable from random absent IDs (404 where a lookup exists); unsupported private actions on /log, fields on /records/blob stages, private archive imports or private wraps are rejected before storage. JSON keys and encrypted inner bytes on hostile ordinary records are never interpreted as private actions; such arbitrary member ciphertext does not become a supported private storage path. No new link show/search/download/write route is introduced. Structural transport tests must allow only the dedicated opaque vault adapter for private persistence, prohibit shared write/export and telemetry sinks, and prove that permitted requests contain only padded ciphertext and allowed transport fields, not plaintext or per-artifact markers. Matched empty/populated vault traces must satisfy D36, not merely contain encrypted content.
13. **Browser and CLI/MCP surfaces:** browser offers an explicit private checkbox on new artifacts, a separate author-private indicator/filter, encrypted backup/import and eligible-agent handoff/return import. Show server-backed multi-device access, verified-version/conflict and downloaded-copy limits before first save/handoff; explain when freshness is unconfirmed, never claim offline synchronization or immediate remote revocation. Existing shared create/edit controls remain separate. Private detail supports Stage 1 safe viewer/download, versions, comments, edit/delete, Stage 2 project assignment and cross-journey private-copy workflow with source/destination and observed head visible only to its audience. CLI adds `private init|list|show|create|edit|comment|delete|project|copy|backup|import|handoff|return` and stdio MCP `private_list`, `private_show`, `private_create`, `private_edit`, `private_comment`, `private_delete`, `private_project`, `private_copy`, `private_backup`, `private_import`, `private_handoff`, `private_return`; private init provisions/unlocks the member's server vault through the dedicated adapter, not agent approval or a per-artifact server record. Inputs are explicit local paths/IDs and observed predecessors; no URL fetches, arbitrary recipients, direct grants or uploads to shared storage. Private saves explicitly use the dedicated padded vault transport. Agents need approved verified journey credentials plus eligible encrypted local handoff; normal connection alone never downloads private content. Browser import of agent return requires previously refreshed ordinary contexts and verifies actual actor attribution; the author is not made its writer. Keep ordinary artifact list/search counts separate from optional authorized-private composition and Stage 2 project filters. Preserve credential approval, real-user key protection and header/footer. Agent link tools are not these authenticated tools.
14. **Client/version boundary:** use core/client/interface `0.1.7`, capability `private-v1`, header `X-Private-Format`, authenticated protocol field `privateFormat`, alongside control-proof-v1/artifact-v1/project-v1. New journeys require 0.1.7 and all four capabilities. Existing signed 0.1.4/0.1.5/0.1.6 regression journeys are not purged or silently upgraded; a person guide of either role raises client.minVersion to at least 0.1.7 before private creation/copy/placement in that journey. Every source and destination must meet that boundary. All reads/writes at a private minimum, including ordinary artifacts/blobs/controls, require all four capabilities; authenticated protocol negotiation remains content-free and actionable for older clients. A minimum-raising request must satisfy its resulting minimum. Version/capability claims grant neither private keys nor access; missing/malformed/unknown/too-old versions, unsupported private record/action/bundle and future signed minimum fail before partial views or mutation. Server-run links use running version/capabilities and retain the update-server message; capability support never includes private content. Move unsupported-future fixtures to 0.1.8 while preserving explicit 0.1.3-or-older and 0.1.6-without-private-v1 rejection. Align public core/client manifests, dependencies and lock; leave private server/web package and rules package versions unchanged. Stage 2's 0.1.7 future fixture becomes supported only with private-v1 after this stage. Keep old-history scenarios and do not rewrite signed proofs to change them.

## Criterion homes and proof contract

Every Stage 3 focused suite and negative runner below is a planned deliverable, not an existing test or observed pass. ## Technical-lead decisions (recorded 2026-09-03, closes vault-padding-policy, vault-traffic-policy, vault-checkpoint-bootstrap)

- **Padding:** each member's vault is a fixed set of 64 slots of 1 MiB ciphertext each, allocated in full at join, whether or not it is used. Content, history and private attachments are chunked into slots. A full vault refuses new private content with a clear error. The vault never grows, so its size reveals nothing. Raising the capacity is a later, explicit change for everyone at once.
- **Traffic:** the client syncs on a fixed schedule (when the journey opens, then every 5 minutes while it is open). Each sync re-encrypts and uploads exactly 2 slots plus the signed header, whether or not anything changed. Dirty slots go first; otherwise random slots. A private save waits for the next sync and doesn't trigger one. Reads fetch the header plus 2 slots on the same schedule; the whole vault is fetched only when the journey is first opened.
- **Freshness:** the header carries a version counter signed by the member, and each device keeps the highest version it has seen. A server that returns a lower version is reported as a rollback. A new device gets the current head from the existing device-pairing step. Without a paired device, it accepts the server head and shows that it is unverified until another device confirms it. Divergent heads with the same version are merged per artifact (higher artifact version wins; on a tie, both are kept as conflicting versions), then signed at a higher version.
