# Wayfinding v2: delegable capabilities, library, forum and sensemaking

## Summary <!-- work:summary -->
Extend the deployed PoC (branch `rewrite-poc`) into a usable collaboration space. Any capability a person holds can be assigned to one of their agents, never by default; an OAuth client that the person marks as an agent always acts as that agent. A hosted console lets a person manage agents, cards and passkeys and browse their journeys. The library holds labelled artifacts of many kinds with search; a Discourse-like forum has boards, topics and posts plus a conversation on every project and artifact; sensemaking rounds bring back the formal interview and synthesis exercise. Every coordination change is stepped by gdp-wired rules. Human ontology: `docs/ontology.md`.

## Why <!-- work:rationale -->
Dan (campaign brief, 2026-11): "write the spec and roll with it"; keep the terms guide (journey creator and caretaker), owner (artifact creator) and lead (project creator); make any person capability assignable to an agent but not by default (create journeys, invite, change nickname, remove agents…); use Mobbin for UI patterns; build out the artifact library modelled on pi-artifacts kinds; standardise a common forum with conversations on artifacts and projects; revive formal sensemaking on top of artifacts and conversations. The PoC showed that agent cards cannot be enforced while an agent's client holds its person's token, so delegation needs per-client agent binding plus a console outside the agent's reach.

Design (decided here; Dan reviews later):
1. **Capabilities.** A fixed catalogue in `packages/rules/src/capabilities.ts`, each with a scope (account or journey) and the base authority a person needs (member, write, guide, owner, lead, facilitator). Account scope: `journey.create`, `account.nickname`, `agent.remove`. Journey scope: `read`, `artifact.write`, `artifact.delete`, `post`, `topic.create`, `board.manage`, `project.create`, `project.edit`, `task.manage`, `round.create`, `round.run`, `round.contribute`, `member.invite`, `member.admit`, `member.remove`, `journey.policy`, `grant.issue`. Never assignable: adding agents, binding clients, changing cards, managing passkeys.
2. **Cards v2.** An agent's card is a set of capabilities (empty at creation). Effective permission = person holds it now AND card contains it AND person live AND agent live. Narrowing works anywhere; widening requires a verified passkey assertion over the new card's digest (WebAuthn, our own relying party `poc.wayfinding.support`, @simplewebauthn/server). Agents are account-level (one card per agent) and are members of the journeys their person adds them to.
3. **Per-client agents.** AuthKit tokens carry `client_id`. In the console a person binds a (subject, client_id) pair to one of their agents. A bound client always acts as that agent: it cannot omit or replace the agent identity, cannot reach console actions, and its calls are refused when the agent is removed. Unbound clients act as the person. `actingAgent` on tool input remains for unbound clients and is checked as today.
4. **Console.** Server-rendered pages under `/console` on the same Worker: sign in with AuthKit through a client ID metadata document served at `/console/client.json` (authorization code + PKCE), session cookie (HttpOnly, Secure, SameSite=Lax, signed, 8h), CSRF token on every form. Pages: home (journeys, agents, connected clients), agent (card with capability toggles grouped by scope, like Plane/Devin connected-app permissions), passkeys, journey (members, library, forum, rounds read views). Widening a card or binding a client requires a fresh passkey assertion.
5. **Library.** Artifact metadata gains kind (markdown, html, pdf, code, image, video, audio, data, link, skill, prompt, agent, applet, other), description, labels, optional project, visibility (members or private to the owner), storage (`server` text body up to 256 KiB for PoC, or `sealed` MLS blob through the proxy), and for links a URL and summary. Search over name, description, labels and server text (simple token match). Owner or guide deletes; writers version with base-version check; owner sets visibility.
6. **Forum.** Boards (guides manage), topics (members with `topic.create`), posts (members with `post`), replies by quoting a post id, edit own post, guide hides a post, topic author or guide locks/unlocks. Every project and artifact has one attached topic created on first post. Author kind (person or agent) is stored and shown.
7. **Sensemaking rounds.** Fields and lifecycle as in `docs/ontology.md`: facilitator = creator; status planned → open → synthesising → closed (facilitator may reopen synthesising to open); participants default all members, facilitator adds/removes any member any time; per-participant interview record private to that person and their agents until they share it with the round; facilitator may assign an artifact as a participant's interview document; contributions to the round document only by participants while open or synthesising, attributed to the person even when an agent writes; `round_next` creates a planned round from a closed one. Default guidance for a "first position" round comes from the site's interview script.
8. **Views.** MCP Apps views for library, forum (boards → topics → thread), round, agent capabilities (read-only, with a link to the console). Patterns from Mobbin: Featurebase/Meetup forum lists, Plane/Base44 comment sidebars, Gumloop/Dropbox Dash library filters, Plane/Devin connected-app permissions, Maze/Wrangle interview sessions and summaries.
9. **PoC privacy deviation.** Post bodies, interview notes, contributions and `server` artifact text are readable by the server so cloud clients can use them; views say so. Sealed storage stays available through the proxy. Real users and confidential data stay blocked by the existing review-launch gate.

Hard constraints: no `gate(` or `compiled(` in server source; all rule values below 2^53; exact dependency pins; no stored state migration needed (PoC data may be reset by redeploying fresh Durable Object class names if the rules hash changes); every rule law has a broken variant that the tests refuse.

## Open decisions <!-- work:decisions -->

## Acceptance criteria <!-- work:criteria -->
- v2-rules: gdp-wired models exist for capability cards (capability set, signed widening, effective check), client binding, library artifacts v2, forum (board, topic, post) and sensemaking rounds (status, participants, interview privacy, contributions), each law with a plain-language comment and a broken variant; every step law is proven from any stored state, and `npm run check:rules`, `npm run typecheck` and `npm test` pass.
- v2-agents: Against the in-process app with synthetic AuthKit tokens, a client bound to an agent acts only as that agent; an agent with an empty card is refused every capability; after the person ticks `post` with a valid passkey assertion the agent can post and nothing else; widening without an assertion, through MCP, or with an assertion over a different card is refused; removing the agent or the person stops the bound client at once; account capabilities (create journey, nickname) are refused to agents without them.
- v2-console: The console signs in through AuthKit with PKCE using its client metadata document, sets a hardened session cookie, rejects form posts without the CSRF token, registers a passkey, and changes a card and a client binding only after a fresh assertion; a bound agent client's token cannot open console pages.
- v2-library: Members create, version, label, describe, search and filter artifacts of every kind; project artifacts are hidden by the default filter; private artifacts are invisible to other members and their agents; only the owner or a guide deletes; links carry URL and summary; server text over 256 KiB is refused.
- v2-forum: Boards, topics, posts, replies, edits, hiding and locking follow the rules; each project and artifact has exactly one attached conversation; posts show author and author kind; an agent posts only with `post` on its card.
- v2-sensemaking: A facilitator creates a round with goal, guidance, document and related artifacts; participants default to all members and can be added any time; interviews stay private until shared; contributions are accepted only from participants while open or synthesising and are attributed to the person; `round_next` starts the next round; the default first-position guidance is available.
- v2-views: MCP Apps views for library, forum, round and agent capabilities load from new versioned `ui://` URIs (released URIs unchanged), act only through tools, and pass the apps host tests.
- v2-live: Deployed to poc.wayfinding.support; a live end-to-end run with Dan's agent identity exercises binding-free agent use, library, forum and a sensemaking round; `docs/poc-test-guide.md` explains the console, agents, library, forum and rounds.
